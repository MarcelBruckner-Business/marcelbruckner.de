Running Home Assistant with Claude, and making sure nothing gets lost

My 3D printer draws 16 watts doing nothing. On 18 November it did that for three hours and 23 minutes after the print was done, because nobody walked over to switch it off:

So I asked Claude, in one sentence, to switch the printer’s plug off ten minutes after a print finishes. A minute later the automation existed in my Home Assistant. This post is about what happened in that minute, why I trust it, and what I built around it so that nothing gets lost and I notice when something breaks. At the end there is a tutorial if you want the same.

One sentence, one automation

Claude talks to my Home Assistant through ha-mcp, an MCP server that runs as an integration inside Home Assistant itself, installed through HACS. Claude sends a request, ha-mcp turns it into Home Assistant’s own API calls.

For the printer, Claude searched my entities, found the printer’s status sensor (finish when a print is done) and the plug, and wrote this (entity names simplified):

triggers:
  - trigger: state
    entity_id: sensor.druckstatus
    to: finish
    for: { minutes: 10 }
    not_from: [unavailable, unknown, offline]
conditions:
  - condition: state
    entity_id: switch.3d_drucker
    state: "on"
actions:
  - action: switch.turn_off
    target: { entity_id: switch.3d_drucker }

The detail I like most is something I did not ask for. ha-mcp ships a best-practices guide for Home Assistant, and in its strict mode it refuses any write until the guide has been read: the guide contains a key that changes every hour, and a write without the current key is rejected. So Claude cannot “just quickly” write an automation the way it half-remembers from 2023; it has to read how Home Assistant wants it done today first.

It still was not perfect on the first try, and the line not_from is the proof. The first version had only to: finish. That evening Home Assistant restarted, the printer’s status came back from unavailable to finish, and to the automation that looked like a print that had just ended. It would have switched off a printer nobody had touched. Switching the printer on does the same, because it reports its last status (finish) after being offline. Claude found this in the history the same evening, and the fix is one line. I mention it because it is the honest picture: the assistant is fast and careful, and a change that goes live immediately still needs a safety net.

Nothing gets lost

There are two different things that can go wrong, and they need two different answers.

The machine dies. Home Assistant runs as a virtual machine, and every night its whole disk is backed up; a second machine keeps a copy, and a third copy goes offsite. That restores everything, but it cannot tell me what changed.

An automation breaks, or a change was a mistake. For that I want history: a diff, with a date. So once a day a small job copies Home Assistant’s YAML into a private git repository and commits when something changed.

The copy is an allowlist: configuration.yaml, automations.yaml, scripts.yaml, scenes.yaml, packages/, blueprints/ and the ESPHome device files. Never secrets.yaml, never .storage/.

The first snapshot still pushed two secrets. A login secret for one integration had been written straight into configuration.yaml, and an ESPHome device had its API key inline. Neither file was on any deny-list, because the problem was not the file, it was a line in it. The repo was private, I deleted and recreated it anyway, and since then the job refuses to push in three cases:

  1. The copy is empty. A moved or empty /config would otherwise “delete” my whole config in git.
  2. A value sits under a key named like a credential (password, token, key, …) and is not !secret, a template or empty; or there is a Bearer header or a URL with a password in it.
  3. Any value from secrets.yaml appears anywhere in the copy, under whatever key. This one I added on 18 November, and I took the idea from someone else.

Why I did not use Git Exporter

There is a Home Assistant app (formerly add-on) called Git Exporter that does roughly what my job does, installed with a few clicks. I read its code before switching to it. Its secret check is better than my first one: it turns every value in secrets.yaml into a search pattern, which is exactly check 3 above. Everything else made me stay: its last release was in 2024, it reports error on every run where nothing changed (so a real failure looks like a quiet day), and it can only push with a personal access token tied to my account. So I borrowed the idea and left the app.

How I notice

A backup nobody checks and an automation nobody watches are hopes, not systems. Home Assistant has a built-in Prometheus export; my Prometheus reads it every minute and Grafana turns it into a dashboard and four alerts that reach my phone through ntfy:

  • Home Assistant does not answer for 5 minutes.
  • A battery is below 20 %, one message per device.
  • A battery device has been unavailable for 24 hours. A dead Zigbee sensor rarely reports 0 %; it just disappears.
  • No successful config snapshot in 26 hours.

The battery alerts carry a label that holds them between 22:00 and 07:00. Nothing about a battery needs to wake anyone up; they arrive with the morning coffee instead.

And the first look at the batteries was a to-do list: four devices under 20 %, one at zero.

The dashboard also lists every entity Home Assistant currently calls unavailable. On the first evening that was 529 of them: leftovers of removed devices, integrations that lost their login, things that are simply switched off. That is not an alert, it is a list I sweep through now and then.

Tutorial: the same for your Home Assistant

You need a Home Assistant OS or Supervised install (for apps), a GitHub account, and a Linux machine that is always on (a Raspberry Pi is fine).

1. Let Claude manage Home Assistant

  1. Install HACS if you do not have it.
  2. In HACS, download the integration HA-MCP (homeassistant-ai/ha-mcp), restart Home Assistant, then add it under Settings → Devices & services.
  3. Connect your Claude client to it as described in the project’s README. Reach Home Assistant over HTTPS only.
  4. Turn on its strict best-practices mode if your version offers it as an option, and ask Claude for something small first. Read what it wrote in the automation editor.

Changes go live immediately. Do steps 2 and 3 before you let it change anything important.

2. Put your config into git, safely

In Home Assistant, install the Terminal & SSH app. In its configuration, add your Linux machine’s public SSH key to authorized_keys, add rsync to its packages, and map port 22 in its network settings.

On GitHub, create a private repository and add a deploy key with write access (a separate SSH key that can push to this one repository and nothing else). Clone it on your Linux machine.

Save this as /usr/local/bin/ha-git-snapshot.sh and set HA and REPO at the top:

#!/usr/bin/env bash
# Copy Home Assistant's YAML into a git repo once a day, refuse anything that
# looks like a secret, commit only when something changed, push.
set -euo pipefail
HA=root@homeassistant.local      # your Home Assistant
REPO=$HOME/homeassistant-config  # a clone of your private repo

cd "$REPO"
git pull -q --ff-only || true

# 1. The allowlist: your hand-written YAML, never secrets.yaml or .storage/.
rsync -a -m --delete --exclude=.git/ --exclude=README.md \
  --exclude=secrets.yaml --exclude=.storage/ --exclude='/esphome/.*' \
  --include=/configuration.yaml --include=/automations.yaml \
  --include=/scripts.yaml --include=/scenes.yaml \
  --include='/packages/***' --include='/blueprints/***' \
  --include=/esphome/ --include='/esphome/*.yaml' \
  --exclude='*' "$HA:/config/" ./
[ -f configuration.yaml ] || { echo "empty copy, refusing"; exit 1; }

# 2. A password written inline instead of through !secret.
if grep -rnEi --include='*.yaml' \
     '(password|token|api_key|secret):[[:space:]]+[^[:space:]!{"'"'"']' . ; then
  echo "inline secret above: move it to secrets.yaml and use !secret"; exit 1
fi

# 3. A value from secrets.yaml that shows up anywhere (whatever the key).
SECRETS=$(mktemp); trap 'rm -f "$SECRETS"' EXIT
ssh "$HA" cat /config/secrets.yaml 2>/dev/null \
  | sed -nE 's/^[^#:]+:[[:space:]]*"?([^"#]*[^"#[:space:]])"?.*$/\1/p' \
  | awk 'length >= 8' > "$SECRETS"
if [ -s "$SECRETS" ] && grep -rlF -f "$SECRETS" --exclude-dir=.git . ; then
  echo "a value from secrets.yaml is in the files above"; exit 1
fi

# 4. Commit and push only when something changed.
git add -A
git diff --cached --quiet || { git commit -qm "snapshot $(date +%F)"; git push -q; }
echo ok

Run it once by hand and look at what landed on GitHub: no secrets.yaml, no .storage. Then let cron run it daily:

0 4 * * * /usr/local/bin/ha-git-snapshot.sh >> /var/log/ha-git-snapshot.log 2>&1

I ran exactly this script against my own Home Assistant (into a local test repository) before publishing it, and fed both checks a planted password and a planted secret value: both refused. It is a simpler sibling of what I run myself, which adds tests, a staging copy that is checked before it touches the repo, and an alert when it has not succeeded for a day.

3. Watch it from Grafana

If you already have Prometheus and Grafana:

  1. Add this to configuration.yaml and restart Home Assistant: 
    prometheus:
  namespace: homeassistant
  2. Create a separate user for Prometheus (Settings → People, not an administrator, local network only), log in as that user once, and create a long-lived access token under Profile → Security. Be aware it is not read-only: Home Assistant has no read-only users, a non-admin can still switch devices. Keep the token like a password.
  3. Scrape it: 
    - job_name: homeassistant
  scrape_interval: 60s
  metrics_path: /api/prometheus
  authorization:
    credentials_file: /etc/prometheus/secrets/homeassistant-token
  static_configs:
    - targets: ['homeassistant.local:8123']
  4. In Grafana, alert on up{job="homeassistant"} below 1 for 5 minutes, and on homeassistant_sensor_battery_percent below 20 for 30 minutes. Leave out your phones and tablets with a label matcher such as entity!~"sensor[.](https://notefeed.me/r/marcelbruckner/my_phone|my_tablet).*": they cross 20 % every day.

One thing that cost me a deploy: write sensor[.] and not sensor\. in PromQL. Prometheus uses Go string escaping and rejects \..

What I would tell someone starting today

  • Let the assistant do the typing, and keep the safety net yourself: a nightly backup for disasters, git for history, alerts for silence.
  • Check what your history pushes. My allowlist was right and still leaked, because the secret was in a line, not a file.
  • Before installing the convenient tool, read its code. Sometimes you keep the idea and leave the tool.
  • Alert on batteries, but not at night.
