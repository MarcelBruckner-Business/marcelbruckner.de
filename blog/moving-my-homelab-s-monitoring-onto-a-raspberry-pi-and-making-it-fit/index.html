Moving my homelab's monitoring onto a Raspberry Pi, and making it fit

Until mid-November, everything that watches my homelab ran on the homelab itself. DNS (AdGuard), the reverse proxy (Caddy), sign-in (Authentik) and the whole monitoring stack (Grafana, Prometheus, InfluxDB, Loki) were containers on my one Proxmox server, a Beelink mini PC that runs every service we use.

Why it moved

When the Beelink went down once, it took everything with it at the same moment. DNS stopped for the whole flat, nothing could send an alert, and there was nothing to open to see what had happened before it died.

So the goal became: when the server dies, a phone alert still arrives, DNS keeps working, and Grafana and the logs can be opened from home or away, while the server is still down. For that, all of it has to live on a machine that isn’t the server. That machine is a Raspberry Pi 4 with 4 GB of RAM and an SSD, which I call monitor-pi.

  • What moved: AdGuard, Caddy, Authentik, CrowdSec, Grafana, Gatus (uptime checks), and the stores for every metric and log the homelab produces, with their history.
  • Caddy and Authentik had to move too. Reaching Grafana from outside while the server is dead needs the proxy and the sign-in off the server as well.
  • Measured beforehand: AdGuard, Grafana and the stores used about 1.3 GiB on the server, against 3.6 GiB available on the Pi. It fit on paper.
  • Moved on 2026-11-16.

It didn’t fit

The first day looked fine: swap reads on the Pi were around 30 pages per second. After its first restart, they jumped to around 1,900 pages per second and stayed there. Every program kept pulling its memory back from the SSD, and DNS and everything behind the proxy got slower.

Two things made it worse than the estimate:

  • Caddy, Authentik and CrowdSec weren’t in the 1.3 GiB. Authentik alone (server, worker and its Postgres) holds about 800 MiB.
  • On the server nobody had looked at how much RAM this stack costs: with 28 GB, it never mattered. On the Pi it was the whole budget.

Why the first day fit and the restart didn’t is still unknown.

The goal

“No frequent swapping, only if there is extensive workload running there.” Written down so it can be checked: swap reads below 50 pages/s in at least 95 % of the hours of a normal week.

How full swap is doesn’t matter. Swap still holds about 1.5 GiB today. What costs time is reading it back. So I measured the read rate (pswpin), and how much time programs actually stall waiting for memory (PSI).

Step 0: measure before changing anything

  • PSI (Pressure Stall Information) on. Raspberry Pi kernels ship it off, so it took a kernel flag and one reboot.
  • Per-container swap reads every minute, from each container’s cgroup (workingset_refault_anon), because the host’s counter doesn’t say who is reading back.

There was no single culprit; the whole box was short. Grafana, InfluxDB, Prometheus and Authentik led the ranking. AdGuard was surprisingly high too: its memory reservation turned out to be best-effort only, so the kernel swapped it out as well.

The path

What replaced what

The collector was picked by a trial on the same host (median memory): Fluent Bit 15 MiB, Vector 46 MiB, Alloy 97 MiB.

Nothing had to be torn up for the switch:

  • VictoriaMetrics scrapes the same targets Prometheus did, and accepts InfluxDB’s line protocol. Every Proxmox host, backup server and script kept its own write-only token, now checked by vmauth.
  • 33 alert queries and 100 dashboard queries were rewritten from Flux to MetricsQL. Each one was compared against the original on the same data before the switch.
  • One VictoriaLogs datasource replaced 25 Loki ones.
  • The old data stays on the Pi for 30 days in case I need to roll back.

The trend so far

Every hour since the switch has been under the goal (median 20, max 28 pages/s, 11 hours so far). Memory PSI went from 6–18 % to at most 0.2 %. Still, these were night hours. The verdict comes after a full week, on 2026-11-27.

What went wrong on the way

  • Grafana crash-looped for about 3 minutes. Renaming a provisioned datasource while keeping its id is refused.
  • The Beelink’s logs were dropped for about 7 minutes. VictoriaLogs reads Loki’s tenant header as a number and answered “400” to a name.
  • 14 of 18 hosts’ container logs were missing for about 3 hours. Their Docker logs to the journal, not to files. Only 4 hosts showed up right after the rollout, and we put it down to a quiet night instead of checking. Fixed, and the gap was refilled.
  • A JSON import answered 200 and stored nothing. It was missing one Content-Type header.
  • The nightly backup failed once on a leftover step from the day before. It was rerun and verified.
  • And one good find: an “offsite backup stale” alert had been false all day. The old Flux query silently ignored half of the runs.

Lesson: after switching a pipeline, count the rows and the hosts that arrive. A 200 isn’t proof.

Next

  • 2026-11-27: the week’s verdict, then a tighter swap alert.
  • Maybe Grafana itself (~650 MiB) → vmalert + Alertmanager + Perses (~60 MiB). Only if the week says it’s needed.
  • Maybe Authentik → Authelia: lighter, and configured from one file.
