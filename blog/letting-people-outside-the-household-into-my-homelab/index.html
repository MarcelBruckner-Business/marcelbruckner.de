Letting people outside the household into my homelab

Until this month, everyone with an account on my homelab lived in our flat. That made a lot of things easy without my noticing. Then a friend and I started a trading lab together, and my dad may get a cloud folder later. Neither of them should see the rest of the homelab, and neither should see the household’s own domain at all. This post is about what that took on the sign-in side.

Accounts that opened everything

Every app sits behind Authentik, reached through Caddy. Authentik has one default that only matters once there are strangers: an application without a policy binding is open to every signed-in user.

When I counted, 39 of my 43 applications had no binding. An account for my friend would have opened Home Assistant, the cameras, the photos, the documents, Proxmox and Grafana. Nobody had noticed, because the only accounts were the two of us.

The fix is boring on purpose:

  • Every application is bound to a group: the household apps to the household group, the trading apps to a trading group, later the cloud folder to a group just for my dad.
  • Who is in which group lives in one file in git, next to the bindings.
  • The deploy fails when an application has no binding. A new app can’t be open by accident; someone has to decide who gets in.

I ran an access matrix before and after: every user against every application. The two household accounts got the same answers as before on all 43 apps. A test user in no group was refused everywhere.

A second front door

Outsiders get their own domain, marceltov.de, with its own sign-in page at auth.marceltov.de. It is still one Authentik, with a second brand: its own title, its own password-reset flow, and mails from an address on that domain. I tested the reset end to end with a throwaway user: the mail landed in the inbox, not in spam, and the link pointed to the right domain.

The surprise was the outpost, the part of Authentik that checks every request Caddy hands it. Authentik’s built-in outpost always sends the browser to the sign-in domain it was set up with, whichever domain the app is on. So an app on marceltov.de sent outsiders to the household’s login page. The way out was a second, standalone outpost just for marceltov.de, which can be told where to send the browser. It is one more small container.

flowchart LR
  B[Browser] --> CF[Cloudflare] --> C[Caddy]
  C -->|household domain| O1[Built-in outpost]
  C -->|marceltov.de| O2[Standalone outpost]
  O1 --> A[(One Authentik)]
  O2 --> A
  A -->|group bound to the app?| APP[App]
  A -.->|no binding: deploy fails| X[Refused]

In the Raspberry Pi post I wondered whether to swap Authentik for the lighter Authelia. Brands, groups and outposts are exactly what this needed, so Authentik stays.

Apps that bring their own login

Not every app is happy behind a proxy, and a second login on top of the first helps nobody:

  • Wiki.js signs in with OpenID Connect and maps Authentik’s groups onto its own, so each group sees only its own pages.
  • FreqUI, the trading bot’s web interface, has one shared password and its own login window. Caddy now fills that password in after Authentik has let you through, so nobody types it. The trading post has the details.
  • MCP servers are what Claude connects to from claude.ai, and those connectors sign in with OAuth, which most servers don’t do themselves. The OAuth front I built for Trilium, trilium-mcp-proxy, has grown into mcp-login-proxy (GitHub): one front for any MCP server, with the same Authentik account behind it. OpenBB, Grafana and OpenCloud sit behind it now. For OpenCloud it also fixed an annoyance: its old connector asked for a new sign-in every hour, because its token had no way to refresh.

Docs that outsiders can read

The internal documentation stays where it is. People outside the household get a separate wiki, wiki.marceltov.de, with usage docs only: how to sign in and how to do things, no hostnames, no addresses. Each task is one page with one diagram and its steps.

One thing needed fixing there: Wiki.js 3.5 recognises Mermaid diagrams but doesn’t draw them on pages. A short script in the theme settings does now.

What I took from it

  • A default that’s harmless with two users becomes a hole with three. Make it a rule the deploy checks, not something to remember.
  • Test with the people you are protecting against: a user in no group, a mail to a real inbox.
  • Write the docs for the reader. My friend doesn’t need to know where things run; he needs to know what to click.
