One repo, one home per fact: finishing the homelab consolidation

Today closed out a project that has been running for weeks: turning a pile of per-server repos into one repo for the whole homelab, and then deciding, once and for all, where each kind of documentation lives.

From five repos to one

The homelab used to be spread over main-server, main-pbs, secondary-pbs-pi, proxmox and design. One by one they were folded in: both Proxmox hosts, the local Backup Server and the offsite Raspberry Pi backup box are now configured by Ansible from the same inventory. Today the last one went:

  • design, the shared PlantUML style for the architecture diagrams, stopped being a submodule. Its only other user had already been merged in, so it was pulled in with git subtree add (history kept) and the old repo archived. A fresh clone now renders diagrams without a submodule step, and a style change and its re-rendered SVGs are one commit.
  • The repo was renamed main-server → homelab. It had long stopped being about one server. GitHub renamed it in place, so issues, PR numbers and the 150 ADRs kept their numbers. Every URL in tracked files was rewritten; prose in old ADRs was left as written, because that is history. Nothing that runs depended on the checkout path — every unit, timer and backup hook is installed under /usr/local/lib/homelab/ — and that was checked on every host before the move.

That closes the central-repo programme.

One fact, one home

The bigger change was about documentation. The same machines were described in three places — the arc42 architecture doc, a Trilium wiki and Homelable — and they disagreed. Reading the live hosts against them found the architecture doc wrong about swap and kernels on both hypervisors, about how Frigate detects, how Jellyfin runs and which apps one guest hosts, and the wiki putting an app on the wrong guest.

The rule now:

Knowledge Lives in
Everything about one machine, runbooks Homelable
IP, MAC, CPU, RAM, disk Proxmox (shown in Homelable, never retyped)
Config, resources, firewall, backup jobs Ansible in the repo
Why something was decided an ADR
What went wrong a post-mortem
Architecture across machines arc42.md
General lessons and reading notes Trilium

Everything else links. ADRs and post-mortems stay in git on purpose: they merge in the same PR as the change they record.

What Homelable is

Homelable is a self-hosted, open-source app for documenting a homelab. It does three things that a wiki doesn’t:

  • It knows the devices. It imports machines from Proxmox and from its own network scan, so IP, MAC, CPU, RAM and disk come from the source rather than being typed in. A document is attached to a device, and Homelable marks it as drifted when the device’s facts change after the doc was written.
  • It draws them. Canvases are diagrams built from the same inventory: boxes are real devices, and a box can hold the containers running inside it.
  • It talks to Claude. It ships an MCP server, so a Claude session can search and read the docs, and write device docs, canvases and runbooks, the same way it reads a repo.

That last point is what tipped the decision: the docs are read by the same sessions that change the system, so they are worth keeping current.

How it is set up here

Homelable runs on its own small LXC container (CT 105, 2 GB RAM) on the main Proxmox host, deployed like every other guest: a git repo with one Docker Compose project and a deploy.sh, its secrets pulled from 1Password.

  • Three containers, from the upstream images: the web frontend (nginx), the backend (FastAPI, which also scans the network, hence the NET_RAW capability), and the MCP server.
  • All state is one SQLite file in a Docker volume: inventory, canvases and every document. The guest is in the nightly Proxmox backup, so that file goes through the full chain: local Backup Server, then the Raspberry Pi, then offsite. Its backup has been restored in a drill.
  • Access goes through the existing ingress. Caddy on the network guest publishes it on its own subdomain. Browser sign-in is OIDC against authentik, so it uses the same single sign-on as the rest of the homelab; the authentik provider is a blueprint in git. The MCP endpoint is reached through the same Caddy, with an API key instead of a login. One gotcha there: the MCP server answers /mcp with a redirect to /mcp/, and clients drop the API key on the redirect, so Caddy rewrites the path first.
  • A copy in git, for now by hand. A Sync button writes every document to a private GitHub repo, so the docs survive the host they describe. It has no schedule yet, which is why the restore runbooks still live in the architecture doc in the repo.
  • Monitored like everything else: the five fleet sidecars (logs, metrics, uptime monitor, image updates, dashboard discovery) run next to it.

The honest weak spot: Homelable runs on the host it documents. If that box is down, the docs about bringing it back are in the git copy and the architecture doc, not in the app.

What was built in Homelable

  • 26 device docs, one per machine, all in the same shape: purpose, why it is this way (each line linking its ADR), what runs here, what is special, where its operations differ, troubleshooting backed only by real incidents, dependencies, changelog.
  • 14 runbooks moved over from the wiki and corrected where they had gone stale.
  • A Services canvas: every guest with its running containers, checked one-to-one against docker ps, grouped into seven zones by function. Grouping by host was tried first and read as a pile, since 20 of 22 guests sit on one box.
  • A Backups canvas: 22 guests, which job backs each up and when, three tiers of storage — and, just as visibly, the eight guests that are deliberately not backed up.
  • The old hand-drawn network canvas was deleted; everything on it was already somewhere else.

On the Trilium side, 17 homelab pages were deleted once their content was confirmed in Homelable, and the rest trimmed down to the general lessons.

The lesson

Three copies of the truth don’t give you three times the safety — they give you three chances to be wrong, and no way to tell which one is. One home per fact, links everywhere else.
