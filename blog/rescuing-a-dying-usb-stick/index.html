Rescuing a dying USB stick: recovering truncated files with rsync, photorec & tag-matching

I just rescued a dying USB music stick, and the failure mode is sneaky enough to be worth writing up: a failing FAT flash drive can lie to every copy tool. The directory still lists each file at its original size, but the filesystem can only hand back the first cluster or two. cp, Finder, even rsync all report success while silently truncating your files. Here’s the full runbook (macOS, but the tools are cross-platform).

The symptom that fools you

A flash drive (USB stick, SD card) is dying but not dead. Files are all listed, yet some won’t open — and a normal copy produces files that play for a second and cut off. The dead giveaway: every damaged file ends on an exact multiple of the cluster size (32768 B = 32 KB on mine).

That’s lost FAT cluster chains. FAT stores a file as a linked chain of clusters; when the link bytes rot, the filesystem follows the chain only to the break and stops — but the directory entry still carries the full size, so tools think the copy is complete. A 4-minute MP3 that’s only 32 KB has its header intact (players show full duration) but almost no audio. The tail data usually still sits physically on the flash, reachable only by reading raw sectors.

1. Salvage what’s still readable (no root)

rsync -rt --partial --no-perms --no-owner --no-group \
  --exclude='._*' --exclude='.Spotlight-V100' --exclude='.fseventsd' \
  "/Volumes/NAME/" dest/

--partial keeps half-read files; rsync skips unreadable ones and exits 23 (“partial transfer”). Compare file count and total bytes, source vs dest.

2. Find the silent truncation

Don’t trust the copy — decode-test every file. Anything that errors, or whose size ÷ duration implies an absurd bitrate (< ~40 kbps), is truncated:

ffmpeg -v error -i FILE -f null -     # any output = problem
ffprobe -v error -show_entries format=duration -of csv=p=0 FILE

Confirm with the round-block test: size % 32768 == 0 on the damaged files = cluster-chain loss, not a genuinely small file.

3. Carve the raw flash (needs root)

PhotoRec ignores the filesystem and rebuilds files from their content signatures across the whole device, including free space and orphaned clusters:

brew install testdisk
sudo photorec /log /d OUT/recup /cmd /dev/rdiskN \
  fileopt,everything,disable,mp3,enable,mov,enable,search
  • Use the raw node /dev/rdiskN (faster), find it with diskutil list.
  • mov covers mp4/m4a/3gp; add whatever signatures you need.
  • If the drive stalls on bad sectors, image it first with ddrescue (resumable, gentle) and carve the image instead of hammering the dying device.

4. Rename & re-match the carved files

Carved files come out as fNNNNNNNN.mp3 with no names — but ID3/MP4 tags usually survive. Read artist/title/duration with ffprobe, fuzzy-match (normalised token overlap) back to your truncated originals, keep the largest non-truncated copy per track, and decode-test before trusting it. Bare filenames (11 Represent.mp3) need title-only matching; pin ambiguous ones (Intro, Outro) to the known album artist.

Gotchas

  1. rsync reports truncated files as copied — always decode-test; never trust the byte count alone.
  2. wholedisk is NOT a valid token in photorec 7.2 — it throws a syntax error; the raw device already is the whole disk.
  3. macOS ._* AppleDouble files and embedded cover art (JPEG mislabelled as PNG) trip ffmpeg -v error — ignore them.
  4. Verdict: a dying stick only gets worse. The moment you’ve salvaged it, stop using it — copy to fresh media and retire it. Every extra read risks more decay.

The result

16 GB FAT32 stick, 32 KB clusters, ~879 files. Decode test found 1 dead, 11 unopenable, 181 truncated to cluster boundaries. PhotoRec carved 818 full files from the raw flash; tag-matching healed 179 of 193. Final library: 6.2 GB — bigger than the 4.2 GB the failing filesystem could even show. Then straight onto a fresh SD card, and retire the old stick for good.
