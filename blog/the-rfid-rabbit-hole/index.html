The RFID rabbit hole: why my door fob wouldn't copy

The setup that started it all: a spare Raspberry Pi and an RC522 reader. Looks right for the job. Isn’t.

I inherited an apartment from the previous renter, and with it a little pile of blue key fobs that open the building door. I wanted more of them. How hard can copying a key fob be? Famous last words. What followed was an afternoon of debugging that ended with me learning more about RFID than I ever meant to — and ordering a €23 gadget to do what I’d confidently assumed a Raspberry Pi could.

Here’s the whole detour, because the lesson generalises.

The plan

Cheap, obvious plan: grab a spare Raspberry Pi, wire up an RC522 RFID reader (the ubiquitous blue board everyone uses for exactly this), and read/write fobs from a little script. I set the Pi up properly — Ansible to enable SPI, install the reader library, drop in a rfid command — held a fob to the antenna, and ran a read.

Nothing.

No error, no garbled data. Just silence, like there was no fob there at all.

Ruling things out

My first instinct was a wiring or hardware fault, so I went looking for evidence instead of guessing:

  • Wiring? I hammered the SPI bus with 3,000 reads of the reader’s version register and 2,000 write-and-read-back cycles. Zero errors. The connection was rock solid.
  • Dead reader? No — it happily read the sample card that came in the RC522 kit. The reader worked fine.
  • Weak field? I re-ran the scan at five different receiver gains, from maximum down to low. At every level: the kit’s card answered, the blue fob said nothing.

A reader that works, wiring that’s perfect, and a fob that’s simply not there as far as the radio is concerned. That’s not a bug. That’s physics.

Two radios that can’t hear each other

Here’s the thing nobody tells you when you buy an “RFID reader”: RFID isn’t one technology, it’s (at least) two, on two different frequencies that don’t interoperate at all.

Low frequency (LF) High frequency (HF)
Frequency 125 kHz 13.56 MHz
Common chips EM4100/TK4100, T5577 MIFARE Classic, NTAG, Ultralight
What’s on it a 40-bit ID, nothing more an ID plus writable memory (NDEF for phones)
Security none — the ID is broadcast in the clear can be encrypted (MIFARE keys)
Your phone (NFC) can’t see it reads and writes it

The RC522 is a 13.56 MHz reader. My blue fob is 125 kHz. They’re as mutually deaf as an AM radio tuned to an FM station. No amount of code, gain tweaking or antenna fiddling bridges that gap — it’s a hardware frequency mismatch.

The fob in question. It looks exactly like the 13.56 MHz MIFARE fobs in the RC522 kit — and is, in fact, 125 kHz. You cannot tell by looking.

And those cheap blue teardrop fobs? Almost always 125 kHz EM4100. They look identical to the 13.56 MHz MIFARE fobs that ship with the RC522 kit. Indistinguishable by eye, incompatible by radio.

The one-second field test: hold the tag to your phone with NFC on. If the phone reacts, it’s 13.56 MHz. If nothing happens, it’s probably 125 kHz. (My phone ignored the fob too — consistent with the diagnosis.)

Why I couldn’t just “add” a fob

The clean engineering answer to “I want more fobs” would be to enroll new ones: read each new fob’s ID and add it to the access controller’s allowlist. But I inherited this system — I don’t own the controller and can’t touch its config. So enrolling is out. The only route left is cloning: making a new fob that is byte-for-byte the old one.

For a plain 125 kHz EM4100 system, cloning is genuinely easy, because there’s nothing to crack — the fob just shouts a fixed 40-bit number, and that number is all the door checks. You copy it onto a T5577 blank, which can impersonate an EM4100, and the reader can’t tell the difference. (If the system were doing something cleverer — HID Prox, rolling codes — this wouldn’t work. But a cheap EM4100 setup almost never is.)

The actual tool

So, after all that: not the Pi. The right tool is a 125 kHz handheld copier — the little blue “RFID ID copier” with READ and WRITE buttons. It reads the original and writes a T5577 blank, standalone, no computer, ~€23 with a handful of blanks in the box. I ordered this Sotaiseo one from Amazon.de. Hold original → READ, hold blank → WRITE, test on the door. If the door opens, I can make as many as I like.

The €23 answer: a standalone 125 kHz handheld writer. Two buttons — READ and WRITE — and a pack of T5577 blanks. No computer required.

A €9 USB “reader” would have been a trap, by the way: it reads 125 kHz but can’t write, so it can’t produce a working copy. For cloning you need the writer.

The consolation prize

The Pi detour wasn’t wasted. It now has a tidy little rfid command and a small web UI (English + German, runs as a service, reads and writes from the browser) for 13.56 MHz chips — MIFARE and NTAG. Every write is verified by reading it back, and it refuses to touch the blocks that would brick a chip. Wrong band for my front door; exactly right for NFC stickers and the MIFARE cards I actually do have.

It’s one stdlib-only Python file plus an Ansible playbook, replacing the old Python 2 tutorials that don’t run on current Raspberry Pi OS. Code’s on GitHub: Marceltov/rfid-pi.

The takeaway

When something in the physical world refuses to work and your wiring and code are provably fine, stop poking the code and ask whether you’re even speaking the same language as the thing you’re talking to. “RFID reader” is about as specific as “wireless device.” Check the frequency first — it’s the one fact that decides whether the job is five minutes or impossible.

Next step: wait for the copier, confirm the fob really is the door key, and clone it. I’ll report back on whether the door agrees.
